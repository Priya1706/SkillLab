# SentinelAI – AI-Driven Anomaly Detection in Component Burn-In & Screening

**Problem Statement ID:** 26170  
**Organization:** Indian Space Research Organisation (ISRO)  
**Category:** Software | **Theme:** Smart Automation  

---

## 1. Project Introduction

Electronic components intended for mission-critical aerospace systems undergo High-Temperature Operating Life (HTOL) / Burn-In testing (commonly 168 hours) to screen out early-life ("infant mortality") failures and unstable parts. Traditional quality assurance relies on static datasheet pass/fail limits evaluated at fixed checkpoints. However, **latent defects** frequently pass all static limits while exhibiting subtle multivariate electrical anomalies or accelerating parametric drift.

**SentinelAI** is an end-to-end Python/Flask machine learning and quality-control web platform that detects dynamic electrical anomalies, forecasts 168-hour parametric drift from early 0h and 24h readings, explains every flagged component in inspector-ready language, and persists screening history in SQLite.

> **Demonstration Data Notice:** The default dataset bundled with SentinelAI (`data/sample_components.csv`) is **100% synthetic demonstration telemetry** generated by `data/generate_dataset.py` for screening simulation. It is **not** actual ISRO qualification or flight test data.

---

## 2. Problem Statement & Proposed Solution

### Problem Statement
Static pass/fail thresholds fail to identify components with latent reliability risks when individual measurements lie within specification bounds, and waiting until 168 hours to discover excessive drift delays screening decisions.

### Proposed Solution
SentinelAI implements a decoupled dual-module ML screening pipeline:
- **Module A – Dynamic Anomaly Detection (`IsolationForest`):** Evaluates multivariate electrical telemetry (`iddq_ua`, `leakage_current_na`, `propagation_delay_ns`, `temperature_c`, `Value_0h`, `Value_24h`, and early 0h→24h shift) scaled with `RobustScaler` to detect statistical outliers and subtle multivariate anomalies—even when every parameter passes static datasheet limits.
- **Module B – Time-Series Drift Prediction (`RandomForestRegressor`):** Predicts `Value_168h` strictly from `Value_0h` and `Value_24h`, computes net predicted drift and hourly drift rate, and flags components exceeding a configurable safety slope.
- **Explainable AI (`utils/explanation.py`):** Computes genuine single-feature median ablation attributions for Isolation Forest alongside batch peer z-scores, static limit checks, and drift threshold ratios—presenting transparent, non-causal explanations for QA inspectors.

## 6. Machine Learning Methodology

### Module A – Dynamic Anomaly Detection (`models/anomaly_model.py`)
- **Features:** `iddq_ua`, `leakage_current_na`, `propagation_delay_ns`, `temperature_c`, `Value_0h`, `Value_24h`, and `early_delta_24h` (`Value_24h - Value_0h`). Completely independent of Module B and future `Value_168h`.
- **Scaling & Model:** `RobustScaler` + `IsolationForest(n_estimators=250, contamination=0.14, random_state=42)`.
- **Scoring & Tiers:** Decision function values are monotonically mapped to a `1–99.5` anomaly score:
  - `NORMAL`: score `< 45`
  - `WARNING`: score `45 – 69.9` (borderline band just above the contamination boundary)
  - `ANOMALOUS`: score `>= 70` (below the Isolation Forest contamination boundary)

### Module B – Time-Series Drift Prediction (`models/drift_model.py`)
- **Inputs:** Strictly `Value_0h` and `Value_24h` (expanded internally via `FunctionTransformer` into `Value_0h`, `Value_24h`, `Value_24h - Value_0h`, and `(Value_24h - Value_0h) / 24.0` with zero target leakage).
- **Model:** `RandomForestRegressor(n_estimators=250, max_depth=12, min_samples_leaf=3, random_state=42)`.
- **Data Split:** Reproducible **batch-grouped 80/20 split** (`GroupShuffleSplit` on `batch_id` when 5+ batches exist, falling back to `train_test_split` otherwise) to prevent batch leakage.
- **Drift & Safety Check:**
  - `predicted_drift = predicted_value_168h - Value_0h`
  - `drift_rate = predicted_drift / 168.0`
  - Flagged when `abs(drift_rate) > safety_slope` (default `0.025` units/hour).

## 7. Dataset Description

The synthetic generator (`data/generate_dataset.py`) creates **1,200 component records across 12 batches** (`BATCH-01` to `BATCH-12`) with measurements at `0h`, `24h`, `96h`, and `168h`, covering five behavioral profiles:
1. **Normal (~73%):** Low electrical baseline and saturating burn-in drift.
2. **High Leakage (~8%):** Elevated `leakage_current_na` and `iddq_ua` with mild thermal rise.
3. **Gradual Drift (~8%):** Near-normal `0h` baseline with steady accelerating drift toward `168h`.
4. **Sudden Shift (~5%):** Abrupt step increase in parametric value and propagation delay.
5. **Latent Defect (~6%):** Strictly passes all static datasheet limits (`Iddq <= 45 uA`, `Leakage <= 250 nA`, `t_pd <= 16 ns`, `Temp <= 135 C`, `Value <= 130`), yet exhibits abnormal multivariate behavior and drift.

### Custom CSV Upload Schema
Uploaded CSVs must include:
`component_id, batch_id, iddq_ua, leakage_current_na, propagation_delay_ns, temperature_c, Value_0h, Value_24h`

Optional columns: `Value_96h`, `Value_168h`, `device_type`. When `Value_168h` is omitted, SentinelAI operates in inference-only mode using the persisted drift model.

## 8. Installation & Running (Windows PowerShell)

1. Navigate to the project folder:
   ```powershell
   cd SentinelAI
   ```
2. (Optional) Create and activate a virtual environment:
   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   ```
3. Install dependencies:
   ```powershell
   pip install -r requirements.txt
   ```
4. (Optional) Regenerate the synthetic dataset manually:
   ```powershell
   python data/generate_dataset.py
   ```
5. Start the Flask application:
   ```powershell
   python app.py
   ```
6. Open your browser to:
   ```text
   http://127.0.0.1:5000
   ```

On first launch, SentinelAI automatically generates `data/sample_components.csv` (if missing), trains both ML models, initializes `database.db`, and persists the initial screening run.

## 9. Example Usage

1. Open `http://127.0.0.1:5000` (**Data & Pipeline**) to review the active run or upload a new burn-in CSV.
2. Visit **QA Dashboard** (`/dashboard`) to inspect anomaly counts, leakage distributions, 0h→168h drift curves, Actual vs. Predicted `Value_168h`, and batch risk stacks. Adjust **Safety Slope** or **Contamination** and click **Apply & Re-Run**.
3. Open **Components** (`/components`) to search by component/batch, filter by `STATIC PASS` + `HIGH RISK` to isolate latent defects, sort by Anomaly Score, and click **Details**.
4. On **Component Analysis** (`/analysis/<component_id>`), inspect the predicted 168h drift envelope, Isolation Forest ablation contributions, batch z-scores, and QA explanation.
5. Open **Batch Reports** (`/reports`) to compare batch yields, audit previous SQLite runs, and export filtered CSV or PDF QA summary reports.

## 11. Limitations & Future Improvements

- **Synthetic Training Basis:** Demonstration thresholds and distributions are synthetic; deployment on live aerospace burn-in lines requires calibration on historical flight-lot telemetry.
- **Unlabeled Inference Assumption:** When uploading a 24h-only CSV without `Value_168h`, Module B relies on the previously trained Random Forest model and assumes compatible parametric scaling.
- **Future Enhancements:**
  - Support multi-parameter time-series forecasting across all electrical channels (e.g., $I_{DDQ}(t)$ and leakage(t)).
  - Add batch-specific drift baselines and Weibull / Arrhenius reliability life projection.
  - Integrate user role management and automated alert webhooks for chamber telemetry streams.
